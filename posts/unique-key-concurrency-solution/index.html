接口生成唯一键值对并发问题

Posted Mar 1, 2026
By Mercury
views 2 min read
接口生成唯一键值对并发问题
接口生成唯一键值对并发问题

1. 场景与问题

在设备管理业务中，设备号（Code）和设备名（Name）要求全局唯一。

常规做法： 采用 Check-Then-Act 模式。先 Select 查询是否存在，不存在则 Insert。

问题： 在高并发场景下，存在竞态条件（Race Condition）。两个线程可能同时查到”不存在”，然后同时执行插入。此时依赖数据库的 Unique Key 约束兜底，数据库会抛出异常（如 MySQL 的 Error 1062）。

2. 解决方案分级

  • Level 1（常规）：数据库兜底 + 异常转换

    对于并发度不高的 B 端业务，这种冲突概率极低。我们可以捕获 DuplicateKeyException，将其包装为自定义的业务异常（如 BusinessException(“设备号已存在”)）抛给前端。

    注意：虽然简单，但高频的唯一键冲突会导致 InnoDB 产生大量的间隙锁（Gap Locks），在极端并发下有死锁风险，且异常堆栈构建消耗 CPU。

  • Level 2（高并发）：前置防御

    如果业务对并发要求极高（如秒杀抢注），为了保护数据库，可以使用 Redis 分布式锁 或 布隆过滤器 进行前置拦截，将压力挡在数据库之外。

3. 关于自增主键的思考

对于像”管道编号”这类没有严格业务含义、只要求唯一的字段，直接使用数据库的自增主键是最佳选择。

原理分析：

  • 安全性： 获取自增 ID 的操作是原子的。
  • 性能： 在 innodb_autoinc_lock_mode=1（默认）下，对于简单的 Insert 语句，InnoDB 使用的是轻量级的互斥量（Mutex），分配完 ID 后立刻释放，不需要等待事务提交，性能极高。
  • 副作用： 即使事务回滚，已申请的 ID 不会退还，因此自增 ID 可能会出现不连续（断层） 的现象，但这在非业务强相关的场景下完全可以接受。
